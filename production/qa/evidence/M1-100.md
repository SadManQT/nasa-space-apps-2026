# M1-100 Windows voice readiness handoff

## Cause

The isolated fixture's three-frame check was racing `CampaignAudioDirector._start_voice()`. The caption line id was already correct, but the threaded stream load had not completed, so `voice.playing` was false and `voice.stream` was null. A temporary 250 ms delay before the threaded load completed reproduced the failure on this Mac:

```text
frame 1: playing=false path=<null> line_id=EX-CH01-S01-L01 load_status=3
frame 2: playing=false path=<null> line_id=EX-CH01-S01 load_status=3
frame 3: playing=false path=<null> line_id=EX-CH01-S01 load_status=3
```

See [M1-100_slow_load_before_full.txt](M1-100_slow_load_before_full.txt).

## Fix

`CampaignAudioDirector` now exposes `voice_readiness` (`idle`, `pending`, `loading`, `ready`, `failed`) and emits `voice_ready(line_id)` only after the real stream is assigned and `voice.play()` is called. The fixture waits up to 500 ms for the matching ready state, then keeps the original strict playing/path/line-id assertion unchanged. Duplicate, heard-line, caption identity, and music ducking behavior are unchanged.

The same temporary 250 ms delay passed after the fix: `CAMPAIGN MEDIA RESULT: PASS (114 checks, 0 failures)`. The delay was removed afterwards; it is not part of the product code. See [M1-100_slow_load_after_full.txt](M1-100_slow_load_after_full.txt).
